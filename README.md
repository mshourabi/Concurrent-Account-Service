# Concurrent-Account-Service

پروژه‌ی پیاده‌سازی یک **Code Challenge** برای مدیریت حساب‌ها با استفاده از Java و Spring Boot است.

فایل مربوط به شرح مسئله‌ی Code Challenge در پوشه‌ی `docs` قرار دارد.

</div>

## Technologies

- Java 21
- Spring Boot 4
- H2 Database
- Apache Kafka
- Docker Compose

<div dir="rtl">

## Architecture | معماری

در ساختار دیتابیس، دو جدول اصلی برای `Account` و `Transaction` در نظر گرفته شده است.

برای پیاده‌سازی **Idempotency**، یک `TransactionId` یکتا توسط کلاینت ارسال می‌شود. این شناسه در دیتابیس ذخیره شده و پیش از پردازش تراکنش بررسی می‌شود تا از پردازش تکراری جلوگیری شود.

فرآیندهای زیر در یک تراکنش واحد دیتابیس انجام می‌شوند:

- اعتبارسنجی نهایی درخواست
- به‌روزرسانی موجودی حساب‌ها
- ثبت تراکنش

همچنین برای مدیریت دسترسی هم‌زمان به رکوردهای حساب، از **Optimistic Locking** استفاده شده است.

## کامپوننت‌های اصلی

### 1. TransactionService

مسئول ثبت نهایی تراکنش‌ها در دیتابیس است.

این سرویس اعتبارسنجی نهایی، به‌روزرسانی موجودی حساب‌ها و ثبت تراکنش را در یک تراکنش دیتابیس انجام می‌دهد.

### 2. BalanceService

مسئول ارائه‌ی APIهای مربوط به موجودی حساب‌ها و انجام اعتبارسنجی اولیه است.

اگرچه اعتبارسنجی نهایی در زمان پردازش تراکنش و ثبت اطلاعات در دیتابیس نیز انجام می‌شود و اعتبارسنجی اولیه ممکن است از نظر فنی تکراری به نظر برسد، با توجه به اینکه در سند Code Challenge به اعتبارسنجی موجودی حساب‌ها اشاره شده است، این بخش نیز اضافه شده است.

علاوه بر این، اعتبارسنجی اولیه می‌تواند به بهبود تجربه‌ی کاربر و ارائه‌ی سریع‌تر خطاهای قابل تشخیص کمک کند.

### 3. Kafka Consumer

با توجه به اشاره‌ی Code Challenge به حجم بالای درخواست‌ها، Apache Kafka به پروژه اضافه شده است.
درخواست‌ها توسط Consumer از Kafka دریافت میشود و امکان پردازش موازی آن‌ها را فراهم می‌سازد.

## Concurrency | مدیریت هم‌زمانی

برای مدیریت هم‌زمانی، دو رویکرد اصلی در پروژه استفاده شده است:

### 1. تراکنش اتمیک دیتابیس (Atomic Database Transaction)

اعتبارسنجی نهایی، به‌روزرسانی موجودی حساب‌ها و ثبت تراکنش در یک تراکنش واحد دیتابیس انجام می‌شوند.

در صورت بروز خطا، تمام تغییرات مربوط به آن تراکنش Rollback می‌شوند. به این ترتیب، از ثبت ناقص اطلاعات و ایجاد وضعیت ناسازگار در دیتابیس جلوگیری می‌شود.

### 2. قفل‌گذاری خوش‌بینانه (Optimistic Locking)

برای جدول حساب‌ها یک ستون `version` در نظر گرفته شده است.

با استفاده از Optimistic Locking، در صورتی که چند پردازش به‌صورت هم‌زمان بخواهند یک رکورد حساب را تغییر دهند، تغییرات ناسازگار شناسایی می‌شوند و از نقض یکپارچگی داده‌ها جلوگیری می‌شود.

## Idempotency | جلوگیری از پردازش تکراری

از آنجا که `TransactionId` توسط کلاینت ارسال می‌شود، این شناسه به‌عنوان شناسه‌ی یکتای تراکنش استفاده می‌شود.

فرآیند پیاده‌سازی Idempotency به این صورت است:

1. پیش از پردازش تراکنش، بررسی می‌شود که آیا `TransactionId` قبلاً در دیتابیس ثبت شده است یا خیر.
2. در صورت وجود تراکنش قبلی با همان شناسه، از پردازش مجدد جلوگیری می‌شود.
3. ستون `TransactionId` در دیتابیس دارای محدودیت `UNIQUE` است.
4. اگر دو درخواست با `TransactionId` یکسان به‌صورت هم‌زمان به مرحله‌ی ثبت نهایی برسند، محدودیت `UNIQUE` دیتابیس از ثبت دو رکورد یکسان جلوگیری می‌کند.

> بررسی اولیه‌ی وجود تراکنش به‌تنهایی کافی نیست؛ به همین دلیل، محدودیت `UNIQUE` در سطح دیتابیس نیز در نظر گرفته شده است تا در شرایط رقابتی، یکپارچگی داده‌ها حفظ شود.

## Transfer | انتقال وجه

عملیات `Transfer` موجودی حساب مبدأ و مقصد را در یک تراکنش دیتابیس به‌روزرسانی می‌کند.

از آنجا که تغییرات حساب‌ها در یک تراکنش واحد انجام می‌شوند، **Atomicity** عملیات انتقال تضمین می‌شود. بنابراین، یا تمام تغییرات با موفقیت انجام می‌شوند یا در صورت بروز خطا، تمام تغییرات Rollback خواهند شد.

همچنین، به دلیل استفاده از Optimistic Locking، دسترسی هم‌زمان و ناسازگار به رکوردهای حساب شناسایی می‌شود و در صورت بروز تعارض، عملیات با خطا مواجه خواهد شد.

در این طراحی، برای هماهنگ‌سازی دسترسی به حساب‌ها از قفل‌گذاری بدبینانه (Pessimistic Locking) استفاده نشده است. بنابراین، طراحی بر پایه‌ی Optimistic Locking انجام شده و از ایجاد Deadlock ناشی از قفل‌گذاری بدبینانه جلوگیری می‌شود.




## نحوه‌ی اجرا

ابتدا سرویس‌های موردنیاز را با استفاده از Docker Compose اجرا کنید.

در مسیر زیر، دستور مربوطه را اجرا کنید:

<div dir="ltr">

```powershell
cd Concurrent-Account-Service\docker-compose
docker compose up -d
```

</div>




## Test Execution | اجرای تست‌ها

تست‌های ایجادشده از نوع **Integration Test** هستند؛ بنابراین برای اجرای آن‌ها، **Kafka** باید در دسترس باشد.

### Kafka

برای اجرای Kafka می‌توانید از **Docker Compose** موجود در پروژه استفاده کنید.

در مسیر زیر دستور مربوطه را اجرا کنید:



<div dir="ltr">

```powershell
cd Concurrent-Account-Service\docker-compose
docker compose up -d
```

</div>


### Database

برای اجرای تست‌ها از **H2 Database** به‌صورت **In-Memory** استفاده شده است؛ بنابراین نیازی به راه‌اندازی یا کانفیگ جداگانه‌ی دیتابیس نیست.

داده‌های مورد استفاده در تست‌ها در فایل `src/test/resources/data.sql` قرار دارند. این فایل هنگام اجرای تست‌ها به‌صورت خودکار اجرا شده و داده‌های اولیه‌ی موردنیاز برای تست‌ها را ایجاد می‌کند.

- پیاده‌سازی مدیریت موجودی حساب‌ها
- پردازش هم‌زمان درخواست‌های تراکنش
- حفظ یکپارچگی داده‌ها در شرایط Concurrent
- جلوگیری از پردازش تکراری تراکنش‌ها
- استفاده از Kafka برای دریافت و پردازش درخواست‌ها
- استفاده از Optimistic Locking برای کنترل هم‌زمانی
- تضمین Atomicity در عملیات Transfer
